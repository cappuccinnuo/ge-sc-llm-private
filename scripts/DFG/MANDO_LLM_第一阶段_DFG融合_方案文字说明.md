**一、这个改进点的准确含义**

第一个改进点可以命名为“基于定义—使用分析的语句级数据依赖增强图构建”。它在原来的 CFG/CG 异构合约图中，补充程序值从定义位置流向使用位置的关系，使原 HGT 可以同时利用控制、调用和数据依赖。

这里 DFG 指数据流相关表示。为了与原模型的语句及程序元素节点对齐，实际送入 HGT 的是将定义—使用事实投影到原节点后的 DDG。因此，本方案不是新建一套变量图编码器，而是在同一节点集合上增加关系类型。

设原图为 G0=(V,Ebase)，数据依赖关系为 Edata，则增强图为：

\[
G_D=(V,E_{base}\cup E_{data})
\]

原节点特征提取流程生成 X，检测器计算：

\[
H=HGT(G_D,X)
\]

再将 H 交给原合约检测与节点/行级定位流程。本阶段保持原七类漏洞任务设置。

**二、为什么这些关系可能提供帮助**

CFG 表达可能的控制转移，CG 表达调用关联，但模型仅凭这些边，需要通过若干次邻居传播才能关联相隔较远的定义和使用。直接数据依赖可以把相关语句连接起来，让一次邻居聚合就接收该定义位置的信息。

例如，某次运算的结果流向后续比较，低级调用的返回状态流向检查语句，时间值经局部变量传向返回结果，这些都是定义—使用关系可以表达的上下文。该作用并不局限于重入检测。

这只是机制上的动机。关系错误、依赖覆盖不足、稀疏关系参数和额外边带来的聚合变化，都可能抵消收益，需要与原图及方向消融比较。

**三、第一步：沿用原解析入口，建立稳定身份**

从同一份 Solidity 原始源码生成 AST，并运行原 CFG、CG 和 HCG 构建过程。同时保存每个原节点的稳定 ID、节点类型、源文件、函数身份和源码字节区间。

新增模块使用 AST 建立作用域树，将变量标识符绑定到具体声明。变量身份由源文件、作用域和声明位置共同确定，不能只使用变量名。不同函数的 a、内外作用域的同名变量，不应被当成同一个数据位置。

为了保持原框架的无需编译推理能力，默认使用语法解析和轻量数据流分析。编译器/Slither 可用于可编译样本上的独立参考验证，不是默认推理步骤。

第一版主要追踪函数内值类型局部变量、值类型形参和命名返回变量。状态变量、mapping、数组和 memory/storage 引用等需要额外位置与别名分析，不能直接套用局部标量规则。对未覆盖访问保留统计；无法正确解释控制结构或局部副作用的函数回退为原 HCG。

**四、第二步：把语句拆成读写事件**

对每个语句提取操作、读取位置和写入位置。每次静态写入产生一个固定 def_id，每次读取产生一个 use_id；这些 ID 在固定点迭代前分配。

| 语句 | 读写事件 |
|---|---|
| `uint a = x + y;` | 读取 x、y，然后定义 a |
| `a = 0;` | 定义新的 a，覆盖旧定义 |
| `a += b;` | 读取旧 a 和 b，然后定义新的 a |
| `return a;` | 读取 a，并终止正常函数控制流 |
| `a = f(b);` | 读取调用点的 b，在返回正常时定义 a；不展开 f 内部 |

对于 `uint a;`，应在声明处生成默认初始化定义；命名返回变量在入口初始化。形式参数的入口定义优先映射到原函数入口/函数标识节点。

元组赋值、短路表达式和带副作用的复杂表达式必须按语言规则处理。例如 `(a,b)=(x,y)` 先读取右侧，再写左侧，并保存对应关系；不能假定 x 同时流向 a 和 b。未明确规定的表达式求值顺序不能由解析器随意指定。

**五、第三步：通过到达定义分析建立直接依赖**

只取函数内语义 CFG，不能把 CG 或模型反向边作为执行控制流。对每个分析块 b，保存进入和离开该块时，每个变量可能对应的定义集合。

\[
IN[b]=\bigcup_{p\in Pred(b)}OUT[p]
\]

\[
OUT[b]=GEN[b]\cup(IN[b]-KILL[b])
\]

实现时按块内事件顺序更新更直观：读取不改变状态，写入唯一局部标量位置时，用新定义替换该变量的旧定义集合。分支出口采用并集，循环反复更新直到状态不再变化。

固定点完成后，再遍历读取事件。若 def_id 出现在该次读取所见的对应变量定义集合中，则生成 `def_id → use_id` 事实。边表示 CFG 上可能到达的定义，分支可能使一个读取对应多个定义；它不代表这些关系在同一真实执行中同时成立。

一个例子：

```solidity
uint a = input;   // S1
uint b = a + 1;   // S2
a = 0;           // S3
return a + b;    // S4
```

数据依赖为：S1→S2（a）、S2→S4（b）、S3→S4（a）。不生成通过 a 的 S1→S4，因为 a 的旧定义被 S3 覆盖；也不把 S1 经 b 对 S4 的间接影响自动加入为传递闭包边。

若只有一个 if 分支覆盖 a，分支后的读取可以同时接收旧定义和新定义。循环则可能让文本上较后的赋值影响下一轮较前的条件读取，不能简单按行号向前寻找定义。

**六、第四步：把细粒度事实投影回原 HCG**

定义和读取的位置必须映射回原主图节点。优先使用前端保存的 AST→HCG 引用，否则按源文件、函数、精确源码区间和语法角色匹配。不要按最近行号猜测；同一行可能有多个语句。

为事实保存如下信息：

```text
定义 ID、使用 ID、声明 ID
源节点 ID、目标节点 ID
源文件、函数身份、读写端口
分析来源、支持范围和映射状态
```

送入模型时，以 `(源节点, DATA_DEF_USE, 目标节点)` 合并重复事实。同一对节点因两个变量产生依赖时，首版保留一条模型边，并在辅助表中保留两个变量的事实，避免通过重复边改变注意力。

CFG 和 DDG 即使具有同样端点也应共存；它们的关系类型不同，不能相互覆盖。NetworkX 中间图可使用 MultiDiGraph。语句内部依赖在辅助表中保留，首版默认不新增投影后的 DDG 自环，并报告相应过滤数量。

**七、第五步：形成增强图并接入原 HGT**

在增强图中，原节点特征和标签映射继续使用。新增关系进入元关系字典，例如：

```text
(源节点类型, DATA_DEF_USE, 目标节点类型)
```

HGT 因而可以区分“控制流邻居”和“数据依赖邻居”，使用相应关系参数和注意力处理消息。本阶段沿用其既有消息传递、异构注意力和目标类型聚合，不增加路径编码器或新的辅助训练损失。

公开实现使用自定义 `HGTLayer`，按 canonical relation 三元组索引关系参数。接入时应修改实际图加载与关系字典，而不是假定替换一个标准 DGL HGTConv 就完成融合。[MANDO HGT 实现](https://github.com/MANDO-Project/ge-sc-llm/blob/TOSEM-release/sco_models/model_hgt.py)。

数据依赖的方向尤其重要。原 `reflect_graph` 会以原关系名补反向连接，不能不加区分地用于新增 DDG。正确顺序是：基础边继续按原基线反射；DDG 保持 `DATA_DEF_USE` 正向；可选反向消息显式命名为 `REV_DATA_DEF_USE`。[MANDO 图工具](https://github.com/MANDO-Project/ge-sc-llm/blob/TOSEM-release/sco_models/graph_utils.py)。

特征表、类型内节点 ID、标签表应共享稳定映射。增加边后扩展关系参数表并重新训练，不能直接把旧 checkpoint 当作已学会新关系的模型。训练未见的 DDG 三元组，第一版可按约定省略并统计，而非在测试阶段临时使用随机新参数。

**八、第六步：沿用原检测流程并验证该点的作用**

图分类与节点分类两个模型都应使用同一版本的依赖增强图，输出仍接入原合约检测和细粒度定位流程。保持原各漏洞任务、特征模式、数据划分和训练设置，避免同时更换分类头而混淆贡献。

最基本的三组实验是：原 HCG、HCG＋正向 DDG、HCG＋正向及独立反向 DDG。记录七类逐类效果、宏平均、定位质量、图分析覆盖和额外开销。

开发时先检查覆盖赋值、分支合流、循环、同名声明、源码对齐、多关系共存和方向保持；确定数据依赖确实进入图分类器与节点分类器后，再进行完整训练。不支持分析的函数保留原图，不能丢弃困难样本后只报告较容易子集的结果。

**可用于方案章节的表述**

本方案在 MANDO-LLM 异构合约图的节点体系上引入语句级数据依赖。首先，通过源码解析建立变量声明身份和操作读写信息，在函数内语义控制流上执行到达定义固定点分析，获得考虑赋值覆盖、分支合流和循环传播的定义—使用关系。随后，将细粒度依赖事实映射到原程序节点，以独立有向关系融入原控制流和调用图，构建数据依赖增强的异构合约图。在保持原节点特征与检测流程的条件下，利用 HGT 对新增关系进行消息传递与聚合，为多类合约漏洞检测及细粒度定位提供值传播上下文。
