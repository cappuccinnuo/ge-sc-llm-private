# Prompt 8B 结果复核：标签缺陷、标识符泄漏与访问控制节点级无提升的原因

日期：2026-10-28。审查者：Claude（只读审查，没有修改任何冻结的图、标签、折划分、预测或报告）。
复现脚本：`scripts/DFG/dfg_v2/review/audit_8b_labels.py`，只用标准库，读取已归档的 outer_test 预测、`experiments/ge-sc-data/source_code` 源码，以及 SolidiFI 官方 bug log（DependableSystemsLab/SolidiFI-benchmark，commit 4b0573e1b3f7031396de6f48f7f3e7380222ad3a）。

## 0. 结论摘要

1. **管线计算没有发现错误。** 我直接从 150 个预测 JSON 重新计算了节点任务的折均值和 pooled 混淆矩阵，与 PROMPT8B_REPORT 完全一致（例如 AC 节点 G0：96.175，TP/FP/FN 2922/152/55）。冻结标签与作者的标签规则逐节点吻合（见 §1）。也就是说，我们的代码没有引入标签错位。
2. **所谓“困难文件”主要是作者标签的缺陷，不是模型学不会。**
   - AC buggy_18、AC buggy_26、R buggy_18 三个文件的标签在中途被截断：被注入的漏洞只有前一小段被标为正类。AC 节点 G0 的 152 个 FP 中有 134 个、R 节点 G0 的 295 个 FP 中有 213 个，实际上落在 SolidiFI 注入的漏洞代码上。这些预测是对的，被判为 FP 只是因为标签缺失。
   - AC 节点 G0 的 55 个 FN 中有 35 个是“溢出标签”：状态变量声明、接口函数、合约容器这类不含漏洞的代码被标成了正类。
   - 剩下 20 个 FN 是**全部**非 SolidiFI 的真实访问控制漏洞。五个剖面在这 20 个节点上都是 0 命中（G1R 命中 1 个）。
3. **AC 节点级的 96% 主要来自标识符泄漏。** SolidiFI 注入的函数名和参数名中带有 `txorigin`（重入则带 `re_ent`）。一条不经任何学习的规则——“节点位于名字含 txorigin 的函数内”——在修正后的标签上折均 BF1 达到 98.97，高于所有 GNN 剖面（G0 为 98.77）。重入也一样：该规则为 99.44，G0 为 98.49。
4. 因此，AC 节点“没有提升”，并不能说明 DFG 无用。这个基准测不出 AC 语义上的改进：
   - 可提升的空间几乎全是标签噪声；
   - 真正需要语义理解的 20 个节点，所有模型都不会；
   - 观察到的 −0.2 到 −0.55pp 差值，来自个别折中单 seed 的训练不稳定（见 §4）。
5. **DFG 规划本身**：对重入是对症的，L2 状态读写的增益 10/10 折一致。对访问控制则没有对准，缺少三样东西：
   - modifier 的执行与应用关系（RECON 明确写着“outside phase-one scope”）；
   - 守卫对敏感操作的支配关系；
   - 构造函数身份。

   另外还有一个设计层面的混杂因素：DGL 的 `cross_reducer='mean'` 会把节点类型的所有注册关系一起平均，包括没有边的关系。新增关系会按固定比例稀释原有的 CFG/CG 消息（§5）。
6. 另有两项数据问题：
   - 跨折的重复或近重复合约（buggy_22 与 buggy_36 完全相同，另有多组相似度 >0.99 的样本）落在不同的折里，会抬高绝对分数；
   - 节点任务只含有漏洞文件，不能衡量模型在干净合约上的 FP。

## 1. 作者标签规则的还原与验证

SolidiFI 的 bug log 给出的是**原始文件**的 (loc, length)。图节点的行号来自**去掉注释和空行后**的 cleaned 文件。我按归一化文本顺序把原始行映射到 cleaned 行，再检验下面这条规则：

- 非容器节点：只要节点的行区间与 bug 行区间相交，就标正类；
- contract_declaration：起始行落在 bug 行内才标正类。

| 任务 | 非截断 SolidiFI 文件的节点 | 与冻结标签一致 |
|---|---|---|
| AC 节点 | 6764 | 6755（99.87%；剩下 9 个都是 contract_declaration 容器，规则不一致） |
| R 节点 | 10467 | 10467（100%） |

这说明冻结标签确实就是“bug log 行 → cleaned 行 → 节点”这条规则的产物，我们的管线原样传递了标签。

## 2. 截断：三个文件、一个共同原因

| 文件 | bug log 条目 | 被标注的条目 | 标签截止位置 |
|---|---|---|---|
| AC buggy_18 | 40 | 前 6 条，另加第 7 条的函数头 | cleaned 第 55 行 = 原始第 89 行 |
| AC buggy_26 | 23 | 前 7 条，另加第 8 条的函数头 | cleaned 第 83 行 = 原始第 103 行 |
| R buggy_18 | 42 | 前 6 条，另加第 7 条的首行 | cleaned 第 73 行 = 原始第 111 行 |

全部 80 个 SolidiFI 文件（AC 40 个，R 40 个）中，**只有这 3 个**的 bug log 存在相互重叠的条目：

- AC buggy_18：(86,4) 与 (89,3)；
- AC buggy_26：(100,4) 与 (103,3)；
- R buggy_18：(105,10) 与 (111,6)。

而且三处截止位置都**恰好落在第一个重叠条目的起始行**。其余 77 个文件没有重叠，也没有截断。作者的标注代码不在本仓库，所以这一点只能说与“遇到首个重叠条目即停止”高度一致，不能视为已证实的机制。

（8C 补充）Prompt 8C 发现，这三个文件的正类节点所附带的作者漏洞行列表中，仍有更高的行号（最大分别为 840、687、687），其中 41、23、19 个行号超出了该文件 cleaned 版本的长度。因此“截断”只是观测到的正类缺失模式，作者的转换机制仍然未知。值得注意的是，840 和 686/687 恰好是 R buggy_24 和 AC buggy_24 正类节点的最大行号。附带列表是否来自其他文件，留给 Prompt 8D 核验。

影响：

- AC 节点 G0：buggy_18 的 94 个 FP 和 buggy_26 的 42 个 FP 中，按作者自己的规则补全标签后只剩 2 个，其余 134 个都落在注入的 `require(tx.origin == owner_txoriginN)` 及其函数体上。
- R 节点 G0：buggy_18 的 221 个 FP 中 213 个属于这种情况。
- 这三个文件在另外 9 个折里是训练数据，相当于大约 4–5% 的主导模式被反向标注，所有剖面都受同样的影响。
- 这正是 AC 第 7 折（79.8）、AC 第 8 折（92.1）、R 第 8 折（78.4）偏低的原因。补全标签后它们分别是 98.3、99.5、99.0，节点级折间标准差（报告中约 6pp）大部分由此而来。

## 3. 其他标签问题

- **SolidiFI bug log 自身的行号偏移。** 例如 AC buggy_33 的条目 (8,5) 覆盖到了原始第 12 行 `address public owner;`；(14,4) 从 require 起算，并覆盖到 `address public newOwner;`。buggy_33、42、50 等文件中，状态变量、接口函数和容器因此被标成正类。模型拒绝把这些节点判为漏洞，从代码语义看是对的，却被记为 FN（G0 有 28+7 个）。
- **parity_wallet_bug_2（AC）。**
  - 源码注释标注的漏洞行是 226 和 233，对应 initWallet 和 kill 两个函数。
  - 但这个文件的 cleaned 版本只有 17 行（清洗失败），全部节点标签都是 0。
  - 这个文件的合约级标签是 1，在节点任务里却只能贡献负类。
  - 两个真实漏洞函数的模型概率分别是 0.159 和 0.010。
- **0x627fa62…（R）。**
  - 源码标注的漏洞在第 94 行 `if(_addr.call.value(_wei)())`，对应 cleaned 节点 [75,78]。该节点标签为 0，模型给出 0.987。
  - 被标成正类的却是 changeOwner [6,11]，它与重入无关。
  - 这个文件的 1 个 FP 和 1 个 FN 都是标签错位造成的。
- **两套标注口径并存。**
  - SolidiFI 文件把整个注入片段都标为正类，包括函数头、require，以及 `receiver.transfer(amount)` 这类转账语句。
  - smartbugs 风格文件只标注释所在的那一条语句。
  - 两套口径混在同一个任务里训练和评分。

## 4. 访问控制节点级为什么没有提升

1. **天花板与泄漏。** 修正标签后，G0 为 98.77，不经学习的标识符规则为 98.97。剩余误差：
   - 截断造成的 FP：补全标签后只剩 18 个；
   - 溢出或容器标签：35 个；
   - 20 个真实漏洞：所有剖面都漏掉。

   新关系能改动的只有前两类，而这两类本质上是标签噪声。
2. **真实 AC 节点上没有可比较的信号。** 17 个非 SolidiFI 文件共 20 个正类节点：G0、G2R、G3R、G3 都是 0/20，G1R 是 1/20。训练集中这类正类每折约 18 个，而 SolidiFI 的正类约 2700 个，模型实际学到的是 `txorigin` 这个标识符。
3. **负差值来自哪里。**
   - G3R 的 −0.20 几乎全部来自第 4 折的 buggy_27：G3R 漏掉了 15 条文本完全相同的 `require(tx.origin == owner_txoriginN)` 和 2 个函数头，概率在 0.27–0.47 之间，而 G0 都是 1.00。
   - G2R 的 −0.55 主要来自第 9 折的 buggy_19：G2R 把 22 条 `msg.sender.transfer(address(this).balance)` 判成了正类。在注入片段里，这条语句和 `_recipient.transfer(...)` 是正类，所以模型本来就在利用上下文区分两者。
   - 这些是同一词法模式在不同上下文中的判别不稳定，属于单 seed 的优化差异，不是“数据流有害”。best 与 last 在这项任务上方向相反，也支持这一判断。
4. **语义没有对准。** 本数据集中真实的访问控制缺陷包括：
   - 缺少 onlyOwner 一类的守卫（multiowned、unprotected 等）；
   - 构造函数名写错（incorrect_constructor_name、wallet_03）；
   - 未保护的 selfdestruct 或 initWallet（simple_suicide、parity）；
   - 用 tx.origin 做鉴权（phishable）；
   - 任意存储写（arbitrary_location_write）。

   要判断这些缺陷，需要知道“这个敏感操作是否被基于 msg.sender 和 owner 状态的检查所支配”，以及“这个检查是否通过 modifier 应用到函数上”。
   - L3 的 ENV_FLOW 只表示“哪里用到了 msg.sender”，不表示“哪里被它保护”；
   - L2 能连上 owner 的读写，但没有支配关系；
   - v2 没有建模 modifier 的执行与应用（RECON 中有数百个函数因此回退）；
   - （8C 已核实，更正原表述）在实际训练图中，modifier 调用**根本没有对应的 HCG 节点**：重入 193 处、访问控制 218 处全部如此。原 NX 图中也没有从函数到 modifier 定义的直接或 2 跳路径。原先“逐文件 dot 图中是孤立节点”的说法不适用于实际训练图。结论不变：守卫是否作用于函数，这一信息在图中完全缺失。
   - 构造函数名错误本质上是名字与合约名不一致的问题，与数据流无关。
   - 两层 HGT 的感受野只有 2 跳，“语句 → 状态 hub → 另一条语句”就已用尽。
5. **对比重入（解释 R 为什么有提升）。** G2R 相对 G0 纠正的错误主要在 SolidiFI 的 new_variable 上，正负类都有：注入片段中带的 `mapping(address=>uint) balances_re_ent1;` 是正类，其他状态变量是负类。L2 的读写 hub 让声明节点能看到“我被哪些语句读写”，从而判断它是否属于注入片段。G3R 把 SolidiFI 注入代码上的真实漏判从 41 个降到 12 个。这确实是数据流信息起了作用，但用途是复现 SolidiFI 的片段标注口径。在非 SolidiFI 的重入节点上（33 个正类），G0 为 16 TP / 25 FP，G3R 为 17 TP / 23 FP，差异太小，无法下结论。

## 5. 设计层面的混杂因素：cross_reducer='mean'

作者的 HGTLayer 和我们的 shared_projection 都使用 `G.multi_update_all(..., cross_reducer='mean')`。按 DGL 0.6.1 源码（`heterograph.reduce_dict_data`），它对**所有**指向该目标类型的 canonical 关系的输出做 `stack(...).mean(0)`：

- 没有入边的节点，在该关系上取 0；
- 实际 schema 中，每个已注册关系在全图里至少有一条边（8C 核实）。但对单个节点来说，只要它没有某个关系的入边，该关系仍以零帧参与平均。

每类节点被平均的关系数：

| 节点类型 | G0 | G1R | G2R | G3R | G3 |
|---|---|---|---|---|---|
| expression_statement | 18 | 29 | 31 | 32 | 25 |
| new_variable（AC） | 15 | 25 | 36 | 37 | 23 |
| new_variable（R） | 16 | 26 | 36 | 37 | 24 |

所以在 G3R 中，一条只有 next_line 入边的语句，收到的 CFG 消息只有 G0 的 18/32。状态声明节点更是只有 15/37。

`a_linear` 可以学回一个全局尺度，所以这不是正确性错误。但它改变了初始化尺度，也改变了消息与 skip 残差之间的混合，而且与“新增信息”同时变化。现有的剖面差值无法把两者分开。

## 6. 重复样本

- buggy_22 与 buggy_36 的源码完全相同，在 AC 和 R 中都出现。
- 相似度 >0.99 的近重复：buggy_39/49、buggy_28/38、buggy_33/42，以及 R 中十余组 0x 蜜罐合约。
- 这些对大多落在不同的外层折，例如 AC 节点的 buggy_22 在第 9 折、buggy_36 在第 3 折。
- R buggy_36 没有任何错误，原因之一就是它的完全相同副本在训练集中。

这会抬高所有剖面的绝对分数，也会压缩剖面之间的差异。

## 7. 对结论表述的建议

- 主结果表照旧使用冻结标签，不改。
- 必须同时报告：
  - “作者规则补全标签”下的敏感性分析；
  - 非 SolidiFI 分层结果；
  - 不经学习的标识符基线。
- AC 节点级的结论应写成：“在该基准上无法测出差异（受天花板和标识符泄漏限制）；在真实 AC 漏洞节点上，所有剖面都没有检出能力。”不应写成“DFG 对 AC 无效”。
- R 节点级的 +0.5pp 可以报告为一致的小幅提升，但要注明：提升发生在 SolidiFI 注入片段的标注口径内，非 SolidiFI 子集样本太少，无法检验。

## 9. Prompt 8D 之后的更正（2026-10-29）

- **“AC 节点模型基本是标识符检测器”这一说法过强，现撤回。**
  - 8C 的 idN 改名同时改变了 token 序列的长度和位置。8D 的 B_full 保持每个标识符的 token 数不变，位置不移动。
  - 在 B_full 下，访问控制节点 BF1 仍有 90.1（G0）和 93.4（G3R）。因此 8C 测得的 10% 主要来自原始 token ID 特征对位移的脆弱性，而不是模型依赖名字。
  - 重入节点在 B_full 下降到 60.1（G0）和 67.8（G3R），对名字的依赖确实很大。
  - 以上结论都基于单 seed 的测试时干预。
- **访问控制 SolidiFI 节点的标签本身就能被关键字预测。**
  - 不经学习的规则“节点或所在函数含 `tx.origin`”，在 orig 标签下 BF1 为 95.6，在 C2 视图下为 99.87。
  - 这不算泄漏，因为注入的漏洞本身就是 tx.origin 鉴权。但它意味着该任务已经饱和，在这个数据集上无法用来评价 DFG。
  - 真实的 AC 节点只有 20 个。
- **`buggy_24` 来源假设被否定。** 截断文件附带的作者漏洞行，与 buggy_24 的 Jaccard 只有 0.05–0.06，来源仍然未知。
- **8D 中 F 的设计有误，这是审查者的错误。**
  - 只把标记名替换为 `idN`，会形成一个新的、只在注入代码中出现的名称族。“含 idN 即预测为正”的规则在 C2 视图下 BF1 达到 99.98。
  - Codex 正确地停在了授权点之前。替代方案见 Prompt 8E。

## 10. Prompt 8E 的复核（2026-10-29）

N-real 没有通过预先登记的门槛：
- AC 的 P2 比“全部预测为正”基线高 +9.4pp；
- P3 的 AUC 为 0.643。

审查者从归档的预测中定位了两个原因：
1. **SolidiFI 模板中不含标记的参数名和局部变量名没有被改。** 例如 `amount`、`to`、`receiver`、`_recipient`、`success`、`_weiToWithdraw`。AC 的 P2 正是被这几个名字推高的。
2. **替换名的分布与普通声明不一致。** 由于“不得与文件内已有名字相同”的约束，加上按出现次数加权，替换名偏长、偏罕见。

继续修补抽样方式并反复测试，就落入了“分叉路径”问题，所以基准 v2 的主视图改为全标识符匿名化 N-anon（Prompt 8F）。

N-anon 的代价是，所有文件都失去了名字里的语义，例如 `owner`、`balances`。好处是：
- 它按构造就不含名字通道，可直接验证；
- 它正好隔离出 DFG 所提供的结构信息。

原名基准上的 8B 结果仍保留，用于与 MANDO 原文对照。

## 11. Prompt 8F 的复核（2026-10-29）

8F 按声明绑定做匿名化，在 159/256 个文件上被阻断，原因包括覆盖/重载、成员接收者无法证明、assembly 等。

这是审查者在 8F 中的过度设计。特征视图要去掉的只是“名字内容”这条通道。文件内按拼写一一对应的改名，就能完整保留原文本中“名字是否相同”的结构，而不需要知道每个名字绑定到哪个声明；实体之间的绑定关系本来就由 DFG 边承载。

Prompt 8G 改为文件内按拼写一一对应的全标识符改名（N-anon-s）。核验方式和泄漏门槛都不变。
